## 1. 为什么拆包、以及"包"如何保证不被架空

- 拆分目的：RFC 仍负责"论证充分/可对线"，`packages/` 负责"能照着写完且每步能验"，避免"文档很丰满、开工却卡在细节/顺序/验收不明确"。
- 每份 work package 含三段硬货，缺一不可：
  1. **范围与命中代码**（涉及文件 + 函数/表的精确位置）——没有它就去翻 RFC，避免改错层。
  2. **可执行步骤**（先做什么、怎么做、兼容旧数据怎么办）——不是"我们要 X"，是"改掉这几个点能达到 X"。
  3. **验收标准**（能跑的命令/断言/回归）——"做到什么才算这个包 done"，不是软指标。
- **顺序即编号**：P01–P02 是 rev-3 的 C 级安全/并发地基；P03–P04 把"结构化+sources"两个命根补齐；P05–P07 把多 agent 引擎从"函数链"落到 r/step/Guardian 三个真循环；P08–P10 开放"人可改稿/拿来稿"（rev-3/4 手编与 draft-assist）；P11–P12 是"用户看得到可溯源+知道在干嘛"的前端体验（rev-2/4 UX）。必须先完成上排**其依赖列**的那些包，再开本包。

## 附 · P08（已落地）交付口径 —— "人真的想在稿子上动手"这一层在解决什么

> 一句话：上面那几层（检索多轮、Guardian 三态、RuleVerifier）解决"AI 生成的句子有据、不瞎编"；
> P08 解决的是更靠下的一层——**当作者真要把 AI 句子里当自己稿子来增、删、搬、改时，系统能不能准确听懂"是哪一句"，并让证据不跟着错位。**

### 会在什么情况下遇到它
对政企文案，"生成草稿"常常只是起点：要替换成自家措辞、删去某句、把某段两句挪到前面重说，这恰恰是文秘/办文日常。崩坏点在旧实现：
- 早期只有"改第 i 句 / 末尾追加 / 全文重生成"三个入口，把"一句"表达成**靠位置的下标**；
- 真删掉中间一句 → 后面所有下标集体前移，"改第 3 句"从此悄悄落到别人句子头上；
- 想把某句挪到别处、在某句前插一句 → 系统连这种"操作"都不存在，人直接撞墙；
- "这句出自《XX》第 3 段"的证据仍按序号绑定 → 删/移后证据错挂到别的句子上，溯源反成坑。

> 本质一句：**"用户要动的那一句"是身份，旧代码却当成位置；位置一变身份就散，人一自由就露怯。**

### 宏观方案（以精神、不以代码为纲）
1. **每句给稳定、跨版本的身份**，把"它是谁"和"它排第几"分开——前端/AI 只锚住"这句是谁"下意图，不再靠编号猜。
2. **把"改一份稿"重建模成"一串有序的序列变化"**（增/删/移/改四原子一次落到一个新快照版本）——于是"我批改几处、一次成型、可回放可审"是真，而不是每次都整稿重来。
3. **三条可被测试钉死的不变式托底**：① 顺序可以因搬动而变，但每句的结构归属依旧井然（移动/插入后段内重排、可读可定位）；② 证据随句走（没删就继承、挪走也带源，不随改动错跟）；③ 未授权句永远原样（closed-set，"我删了别处不该让没动的句子悄悄变脸"拿到确定性证明）。
4. **仍走同一套乐观锁 + run 状态机**：手改与 AI 生成/修订共用一地基，并发不写坏、每次 hand-edit 都能一步步回放给人审。

> 对评审/简历的一句话：**"人能自由收拾一篇稿"的地基，是先把"哪一句、加还是减还是挪"这种最底层意图在数据与接口里立成真的一等公民；身份稳定 + 证据随行 + 未授权句不变，才是把"直接改稿"做成可溯源、不退化、可审计的东西。** P08 即为这块地基，已连同真 MySQL 集成测试落地。
