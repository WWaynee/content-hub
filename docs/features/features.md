# content-hub 功能特性文档

> 本文档从**用户使用功能的角度**梳理 content-hub 的功能，作为后续开发的基线。
> 文档状态：**v3 定稿版**。功能边界经多轮确认，已收敛至可进入技术方案阶段。
> 技术实现细节（多 agent 分工、存储模型、数据模型、检索/向量化方案）见 `docs/architecture/`。

## 1. 项目定位

多 agent 架构的**政企内容管理平台**。面向政企单位的普通工作人员和有限的管理员，提供两大能力：

1. **单位内部知识库管理**：管理公/私有的 txt / md 文字资料（类似带目录的网盘）。
2. **稿件生成工作流**：基于知识库检索到的资料，自动生成政企发布的文字稿件（不限定发布平台，用户选择目标平台），并输出稿件与证据原文的对应关系。

核心价值：让生成的稿件**有据可查、来源可溯**——稿件中的文段/数据能回指到知识库中的原始文字片段。

## 2. 角色与权限

单租户（单个企业/单位）下仅两类角色：

| 角色 | 数量 | 权限 |
|------|------|------|
| **管理员** | 每个租户暂时限制 1 个 | 可创建工作人员账号；可操作**公有知识库**和**自己的私有知识库**；其余功能与工作人员完全相同 |
| **工作人员**（普通用户） | 不限 | 只能操作**自己的私有知识库**；创建/操作自己的工作区 |

### 2.1 公有库 / 私有库的访问边界（读写分离）

- **公有知识库**：仅管理员可管理（上传、删除、建目录、更新）。普通工作人员**可预览、可引用**，但**不可下载、不可更新、不可删除**。
- **私有知识库**：每个用户各有一个自己的私有库，**仅本人**可见、操作，**完整读写权**（上传、下载、更新、删除）。管理员也拥有自己的私有库。
- 无论公有还是私有，都是**目录 + 文件**的管理形式。

## 3. 知识库管理

### 3.1 文件类型与内容

- 仅处理**纯文字**：现阶段只支持 **txt** 和 **md**（markdown）两种文件。
- **不含**图片、音视频等非文字内容；知识库处理与稿件撰写工作流均只处理纯文字。

### 3.2 目录与文件

- 结构为**目录 + 文件**的层级管理形式（可创建目录）。
- 底层实际存储使用**阿里云对象存储（OSS）**，文件在物理上是**扁平化**的；目录与文件的层级关系由系统内部维护逻辑映射（技术约束，详见 architecture）。

### 3.3 浏览/预览/下载

- 支持在线预览 / 下载文件。
- **下载权限**：仅私有文档可下载；公有文档仅可预览/引用，不可下载。
- 支持按文件名检索文件（如上传覆盖时选择目标文件）。

### 3.4 上传、覆盖与版本语义

- 用户在自己有权限的知识库（私有库本人，公有库管理员）内上传文档。
- 上传时选择：
  - **新文件**：作为新文档加入知识库。
  - **覆盖已有文件的旧版本**：按文件名搜索 → 选择目标文件 → 作为其新版本覆盖写入。
- **版本语义**：
  - 文件有不可变唯一标识 `document_id`，版本以 **md5** 标识（`version_no` 或哈希）。
  - 文件新旧**只影响可见性和可搜索性**：知识库搜索**默认只搜每个文件的最新版本**；旧版本**不在搜索范围内**。
  - 旧版本文件**后台不删除**，但**当前界面不可见、不可下载**（预留能力，后续可能支持按版本预览，本期不做）。
  - 稿件引用的旧版本证据，因锚点数据保留仍可还原；但**新生成的稿件不允许再引用旧版本**。
- **边界（上传/解析失败兜底）**：
  - 若某版本上传失败，或“上传成功但尚未完成解析 + 向量化入库”，该版本不视为成功。
  - 该文件**最新版本** = 上一次**完整走通「上传 → 解析 → 向量化」全链路**的版本。
  - 只有全链路成功入库的版本，才会成为搜索可见的最新版本。

### 3.5 并发与一致性

- 由于**私有库仅本人可写**、**公有库仅唯一管理员可写**，权限结构**天然消除了两人并发覆盖同一文件**的冲突（一个文件只有一个写入者）。
- 覆盖更新仍以**乐观锁**兜底：覆盖前校验当前最新版本，若已被本写入者之外的变化更新则拒绝并提示重新选择（防御性设计，非功能重点）。

## 4. 工作区 与 需求单

### 4.1 工作区

- 一个工作区 = **一个稿件的生成工作流**；**需求单只是工作区的一部分**。
- 一个工作区对应一个需求单、产出一篇稿件。需要多篇稿件则创建多个工作区。
- 工作区**仅创建者本人**可访问、编辑、操作。
- 用户首页展示其工作区列表，可按以下维度检索（**本期不做全文检索**）：
  - 标题（子串匹配）
  - 标签（候选多选，命中任一即中）
  - 发布平台（多选筛选）
  - 稿件状态（撰写中 / 已生成 / 生成中锁定导出 / 生成失败）
  - 默认按“最近更新时间”倒序。

### 4.2 需求单字段

需求单为**表单**创建，必填字段分两类：

**（1）基础字段（创建时自动生成，用户无需手填）**
- 标题
- 标签（可多个）
- 发布平台（可多个，**枚举写死可选**：微信公众号 / 小红书 / 单位网站 / 微博）
- 创建时间（自动）
- 最近更新时间（自动）

**（2）任务要求字段（必填，用户填写）**
- **稿件风格**：
  - 基调
  - 感情色彩
  - 目标受众
  - 发文目的
  - 禁忌话术 或 其他约束
  - 发文主体（如 学校 / 医院 / 法院）
- **字数要求**
- **章节要求**（用户使用文字说明）

### 4.3 数据来源指定（勾选锁定范围）

- **不需要**用户主动填写“要用什么数据”；由系统根据任务要求**推理**需要哪些数据。
- 用户需在需求单**勾选要引用的知识库范围**，以**锁死检索范围**（仅在勾选范围内搜集/重检测证据）。
- **勾选时公有库与私有库分开勾选**（两个区域/入口，不混为一个目录树）。

### 4.4 对话辅助修改

- 创建需求单时为**表单填写**。
- 界面**一侧可同时对话**，通过 AI 对话修改需求单字段：
  - **可通过对话修改**：稿件风格（基调/感情色彩/目标受众/发文目的/禁忌话术或其他约束/发文主体）、章节要求。
  - **只能手动改选**：字数要求、勾选的文档/目录范围。
- 本质上对话修改都**落回表单字段**。

## 5. 多 Agent 分工

系统采用多 agent 协作，共 **4 个 agent**：

| Agent | 职责 |
|-------|------|
| **知识检索 agent** | 数据搜集阶段：分析需求，在勾选的范围内从知识库检索相关资料，产出供撰写使用的证据素材 |
| **稿件撰写 agent** | 根据需求单 + 检索证据生成稿件，并在写作时**建立「句子 ↔ 检索证据」的绑定关系** |
| **证据整理 agent** | 导出阶段：把已建立的证据对应关系**格式化**输出为证据清单（不做重检，只格式化） |
| **需求对话 agent** | 处理需求单的对话修改；处理**段落级的 AI 修订**（含句子的重新引用检测） |

- 证据对应关系的**实质在撰写阶段建立**；证据整理 agent 仅负责导出时格式化组装。
- 需求对话 agent 负责对话意图理解并落到表单/稿件修改。

## 6. 稿件生成工作流

一个工作区内的稿件生成，一气呵成：

1. **数据搜集阶段**：分析需求单任务要求 → 在勾选范围内，由**知识检索 agent** 搜集相关数据。
2. **稿件撰写阶段**：由**稿件撰写 agent** 根据需求单要求 + 数据搜集产物，生成稿件并建立句级证据绑定。

### 6.1 生成方式

- **一次性全稿**：每次生成都是输出一份完整新稿，**全稿替换**旧稿。
- **一气呵成**：用户发起后自动「搜集 → 撰写」，无中间人工节点。
- **失败处理**：若搜集或撰写中途失败，**保留上一版成功稿件**，状态回到**可导出**，并**提示失败原因**（可重试）。
- **导出锁定**：触发重新生成**期间禁止导出**（旧稿导出锁定），直到新稿生成完成（或失败回退到可导出）。

### 6.2 稿件参考来源标注

- 数据搜集中间产物**不单独设界面节点**。
- 稿件展示界面**标注每个有证据引用的句子的参考来源**（对应到知识库原文），并随证据清单一同导出。

### 6.3 稿件的修改方式（段落级 AI 修订）

- **禁止任何手动字符编辑**：用户无法在稿件中手写/手改任意字符。
- 用户通过**选中段落 → AI 对话**方式修改指定段落；AI 代为改写。
- **最小修改/绑定/重检测单元 = 自然句**（一期按自然句，不做数据点级）。
- **段落级修改**重检测整个段落；**句子级修改**只重检测那个句子。
- 段落内**未变动的句子，证据绑定原样继承**，不重检、不改动。
- **不做改前改后文本对比**（逐字 diff 无意义）。改动后，由 **LLM + 知识检索联动**判断被改句子是否引用了知识库资料，并进行**重新引用检测**（在勾选范围内查找可靠原文支撑）。
- **一句可绑多证据**：如“昨日最高气温 31℃、较去年同期升 3℃、已发布高温预警”可绑定昨日气温 / 去年同期气温 / 高温预警标准 多条证据。界面与导出均可展现该句全部证据；多证据排序一期**默认按稿件叙述引用先后顺序**。
- **无源句子**：重检测返回无源可匹配时，该句证据状态为**「无证据 / 待人工核对」**，句子**保留**，交互上提示用户该句需人工核对；**不展示“改前引用了什么证据”**。
- 注明：因用户经 AI 对话改稿、且作者无法手写字符，稿件的字符始终由 AI 产生；证据链按上述重检测语义维护。

## 7. 证据清单与导出

### 7.1 证据清单（稿件 ↔ 原文 对应关系）

- 证据清单体现稿件句子与知识库资料的对应关系：每个【绑定了证据的句子】对应一个或多个【知识库原文片段】。
- **溯源锚点**：`document_id + 版本标识(md5)`（不可变）+ **章节标题**（切片阶段尽量提取，取不到留空）。
- **原文片段**：必须是知识库**原始原话**，**不允许任何加工/改写**，用户至少可**复制该片段到原文搜索核对**。
- 证据 = 句子（及其绑定的一个或多个主张/来源）↔ 原始资料原文片段 的对应关系。

### 7.2 导出

- 条件：稿件**生成完成**后即可导出；只能导**自己工作区**的稿件。
- **格式**：以 **Markdown** 为主，输出**单个合并 md 文件**，内容顺序：
  1. **稿件正文**（在前）；
  2. **证据清单**（末尾拼接）；
- 证据清单由**证据整理 agent** 格式化输出（在撰写阶段建立的绑定关系基础上组装）。

## 8. 搜索与可见性规则

- 知识库搜索默认只搜每个文件的**最新版本**。
- 旧版本文件**不可见、不可下载、不在搜索范围**（后台保留不删除）。
- 有效“最新版本”= 完成「上传 → 解析 → 向量化」全链路成功的版本。
- 稿件工作流的检索/重检测范围被需求单勾选的公/私有库范围**锁死**。

## 9. 明确不做的事项（首版）

- **不做**第三方平台互通发布流程（不自动推送公众号/小红书/微博）。
- **不做**审核 / 审批流程（无多级审核、无打回）。
- **不做**图片 / 音视频等非文字内容处理。
- **不做**旧版本文件的界面临预览（预留，后续再定）。
- **不做**全文检索 / 文件内容级搜索。
- **不做**稿件内手动字编辑（严格禁止）。
- 不支持 txt / md 以外格式（不含 PDF / DOCX 等）。

## 10. 技术方案阶段将细化（见 architecture）

> 功能边界已定稿，以下技术细节在架构文档中细化，不影响本期功能主链路。

- 阿里云 OSS 扁平存储 与「目录→文件」逻辑映射。
- 文档切片、章节标题提取、向量化入库与检索实现。
- 句子级证据绑定 / 重检测的数据模型。
- 需求单勾选“目录”是否递归含子目录（倾向递归，待架构确认）。
- 覆盖上传乐观锁、md5 版本标识的落地。
