# content-hub 功能特性文档

> 本文档从**用户使用功能的角度**梳理 content-hub 的功能链路，作为后续开发的基线。
> 文档状态：初版梳理。技术实现细节（多 agent 分工、数据模型）见 `docs/architecture/`。

## 1. 项目定位

多 agent 架构的**政企内容运营平台**，面向政企单位工作人员，用于在微信、微博等公域社交媒体平台发布内容（公众号文章、微博等）的全流程内容管理。

核心价值：让政务/企业稿件**有据可查、来源可溯**——稿件中的数据、条款、政策均来自内部知识库，并可精确回指来源。

## 2. 明确的目标与边界

### 2.1 做什么

- 内部素材导入并构建可检索的知识库。
- 全流程内容生产：需求单 → 任务规划 → AI 撰写 → 审核 → 打包。
- 稿件引用知识库信息时，可检索并精确到**文档 + 章节 + 页码**的引用来源。
- 对话式补充需求、驱动任务生成。
- 两级审核（初审 → 终审），支持按任务粒度打回。

### 2.2 明确不做（首版）

- **不做**与第三方平台（微信/微博/公众号）的互通发布流程——发布由用户手动复制粘贴到公域平台。
- **不做**外部已有的单位文档系统对接：知识库素材由用户**人工上传到本项目**。
- 审核意见支持分点，但首版审核仍由**人类审核员**最终确认（AI 仅辅助）。

## 3. 角色与权限

单租户内存在三类角色：

| 角色 | 职责 |
|------|------|
| **工作人员** | 新建/修改需求单、生成任务规划、触发 AI 撰写、处理打回、执行打包导出 |
| **审核员** | 对稿件进行初审/终审，给出分点审核意见，通过或拒绝 |
| **管理员** | 租户内成员/角色管理、知识库文档的维护（权限本文档先从简，细节后补） |

权限分离原则（政企要求）：**审核人不能是稿件的撰写人本人**。

## 4. 完整工作流（端到端）

```
【知识库】上传文档 → 自动切块/向量化/打位置信息 → 成为可检索引用源
        │
【需求单】新建需求单（标题/目标/平台/字数/格式）
        │   └─ 对话补充需求（沉淀为需求补充记录）
        ▼
【任务规划】由需求单 + 对话补充记录生成任务清单（任务标注：是否需检索引用）
        ▼
【AI 撰写】按任务规划写作；需检索的任务 → 检索知识库 → 注入带引用的素材
        │
        ▼
【提交审核】初审 →(通过)→ 终审 →(通过)→ 待打包
        │  │             │
        │  └─(拒绝)      └─(拒绝)
        │       ↓ 打回执行态（按被拒任务单条处理）
        │       对审核意见再生成任务规划 → 改任务打勾 → 重新提交对应审核环节
        ▼
【打包】markdown 初稿 + 引用依据清单（稿件数据→来源文档/章节/页码对照）+ 审核清单
        ▼
【发布】用户手动复制粘贴到公域平台（本项目不打通）
```

## 5. 功能模块详情（用户视角）

### 5.1 知识库（素材管理）

- 用户上传文档（PDF / DOCX / Markdown 等）作为内部素材。
- 系统解析文档 → 切块 → 向量化 → 记录**位置信息（文档 ID、章节标题、页码）**，构建可检索索引。
- 只有**索引完成**的文档可作为引用来源被检索到；索引中的文档可查看处理状态。
- 知识库文档维护（新增/停用/更新）归属管理员；权限细节后续补充。

### 5.2 需求单

- **新建需求单**：填写标题、撰写目标、目标平台（公众号 / 微博 / …）、字数、格式要求、优先级、对接时段。
- **对话补充**：在需求单生命周期内通过对话补充约束、追加数据/引用要求；对话内容沉淀为**需求补充记录**，作为任务规划的输入之一。
- 需求单状态关联整个生产流程（见第 6 节状态机）。

### 5.3 任务规划

- 由需求单（含对话补充记录）自动生成**任务规划**：
  - 拆分为可执行的任务清单（如“政策依据检索”“开篇草拟”“数据引用段”…）。
  - 每个任务**标注是否需检索/引用知识库数据**。
- 任务清单可人工调整；任务可**打勾标记完成**。
- 审核打回后，可按被拒意见**重新生成任务规划**。

### 5.4 AI 撰写（多 agent 协作）

- 依据任务规划进行撰写。
- 对标注“需检索”的任务，从知识库检索，取**带文档/章节/页码定位**的素材注入稿件，保证数据有据。
- 按目标平台差异化处理：长文（公众号）与短文（微博）使用不同写作模板/策略。
- 生成物为可编辑初稿，可再次生成/覆盖。

### 5.5 审核（两级，支持打回）

- **初审** → 通过后进入**终审**；任一环节拒绝即**打回执行态**。
- 审核意见**分点**给出，每条意见可**关联到具体任务/段落**。
- **打回粒度 = 按任务单条处理**：仅打回被拒意见关联的任务，其余已完成任务保留；工作人员针对被拒点再生成任务规划 → 修改 → 任务打勾 → 重新提交对应审核环节。
- 审核通过后才可进入打包。

### 5.6 打包与发布

- 首版仅做**打包导出**：
  - Markdown 初稿。
  - **引用依据清单**：稿件数据 → 来源文档/章节/页码 的对照表。
  - 审核清单（初审/终审意见与结论记录）。
- 用户手动复制粘贴到微信/公众号/微博等平台发布，**不做智能互通发布**。

## 6. 状态机（需求单生命周期）

```
草稿 ─→ 进行中(任务规划/AI撰写)
        │
        ▼
审核中(初审) ──通过──► 审核中(终审) ──通过──► 已通过(可打包) ──► 已发布
   │ ▲                     │ ▲
   └─拒绝                 └─拒绝
       └─► 打回执行态（按被拒任务单条处理）──再规划/修改──► 重新提交对应审核环节
```

需求单生命周期内挂载：1 个**会话**（对话记录）、1 份**任务规划**（任务列表 + 打勾状态）、一串**审核意见**（分点、关联任务）。

## 7. 关键设计契约（跨环节约定）

- **引用结构**：任何从知识库引用进入稿件的内容，必须携带 `{文档, 章节, 页码, 片段}` 定位，用于最终生成引用依据清单。
- **对话 → 结构的转换**：自由对话补充需求后，需被解析成结构化需求条目，才能进入任务规划。
- **打回原子单元 = 任务**：审核意见按任务关联，打回与重新提交都以任务为最小单元。

## 8. 后续可扩展（本轮不做，仅记录）

- 第三方平台互通发布（自动推送公众号/微博）。
- 引用细粒度进一步精确（段落级/高亮定位）。
- 知识库对接单位既有文档系统。
- 更细的租户级权限与审计日志。
- 多租户数据隔离（当前按单租户设计）。
