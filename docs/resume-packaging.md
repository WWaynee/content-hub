## 二、项目简介（2-3 句话，放在标题下面）

> 基于自研多 Agent 架构的知识库内容生成平台，面向政企场景，实现「需求 → 检索 → 撰写 → 校验 → 导出」的全自动稿件生成工作流。
> 核心特点是**句级证据溯源**——生成稿件的每句话都能回指知识库原文，保证内容有据可查。
> 项目前后端完整实现，包含多租户隔离、乐观锁并发控制、熔断重试、流式进度推送等工程化能力。

## 三、核心技术亮点（分条写，3-5 条最合适）

### 版本 A：详细版（投 Agent 开发岗位用，5 条）

1. **自研多 Agent 混合编排架构**：设计「全局编排器 + 专职子 Agent」的混合架构，Orchestrator 用状态机驱动工作流，4 个专职 Agent（检索/撰写/校验/对话）通过结构化数据契约协作，避免了 LangChain 等框架的黑盒问题，全程可审计可回放

2. **双闸门事实质量保障体系**：实现「撰写前 Claim 覆盖度校验 + 撰写后逐句事实校验」的双层质量闸门；事实校验采用「确定性规则优先 + LLM 近义兜底」策略，数值/百分比等强类型断言用规则判定，杜绝 LLM 自判真伪

3. **Guardian 三态裁决检索引擎**：设计 Guardian 裁决机制（accept / retry / ask_human 三态），带硬预算控制的多轮检索循环，证据不足时自动换角度重查，查不到则转入人工介入态而非硬抛错误，兼顾自动化与可靠性

4. **LLM 调用工程化体系**：实现按负载动态超时（700ms/KB 余量 + 10min 封顶）、每次重试独立预算、三态熔断器（50% 失败率阈值 + 30s 熔断）、指数退避重试等工程机制，保障 LLM 调用的稳定性与容错能力

5. **检索质量优化（混合检索 + Rerank）**：构建三层检索质量优化体系（BM25 2-gram 混合检索 + Rerank 重排序 + LLM 查询扩展），在自建评测基准（20 query × 3 难度等级，真实政企语料）上，Recall@5 从 0.58 提升至 0.89（+30pp），NDCG@5 从 0.57 提升至 0.84（+47%）；策略配置化实现渐进式上线，主流程零风险

> 5. **句子级证据溯源体系**：从文档切片（句末软截断，300 字软上限）→ 句子级向量检索 → 撰写时 inline citation → 逐句事实校验 → 证据清单导出，端到端句子粒度溯源，保证引用来源可查可验

### 版本 B：精简版（版面紧张时用，3 条）

1. **多 Agent 编排与状态机**：设计自研多 Agent 架构，Orchestrator 编排检索/撰写/校验/对话 4 个专职 Agent，实现持久化状态机（run/step 落库），全流程可回放可审计

2. **双闸门质量保障**：实现「Claim 覆盖度预校验 + 逐句事实后校验」双层质量闸门，事实校验采用规则优先策略，数值断言用确定性规则判定，LLM 仅兜底近义场景

3. **LLM 工程化与可观测**：实现动态超时、独立预算重试、三态熔断器等 LLM 调用工程机制；构建进度流式推送体系（Broker 发布订阅 + SSE），生成过程实时可见

## 六、面试常见问题 & 回答思路

### Q1: 为什么不直接用 LangChain / LangGraph？

**回答思路：**
- 第一，Go 生态没有成熟的 LangChain 实现，LangGraph Go 版也不完善
- 第二，自研编排器让我更深入地理解了 Agent 的核心机制——状态管理、工具调用、错误处理
- 第三，政企场景对可控性和可审计要求高，自研编排能做到每一步都落库、可回放，这是框架很难完全满足的
- 当然，LangChain 生态的很多设计思想我也参考了，比如结构化输出、工具调用的模式

### Q2: 双闸门校验具体是怎么工作的？

**回答思路：**
- 第一道闸门（撰写前）：把需求拆成多个 claim（子需求点），每个 claim 先去知识库检索，缺证据的直接阻断，不进入撰写阶段——从源头避免"无据可写"
- 第二道闸门（撰写后）：对生成的稿件逐句分析，提取事实断言（数值、日期、百分比等），然后用规则引擎去原文中验证——从出口拦截编造
- 规则优先的设计：能用确定性规则（字符串包含、数值归一化）判定的，绝不丢给 LLM；LLM 只处理语义近义这种规则搞不定的场景，而且标记低置信度

### Q3: Guardian 的三态裁决是怎么设计的？

**回答思路：**
- 传统的 Agent 检索是二元的——找到 or 找不到。但真实场景中，很多情况是"找得不够好但可以换个角度再试试"
- 所以我设计了三态：accept（证据够了，进入撰写）、retry（不够但有空间，换 query 再搜）、ask_human（无论如何都找不到，交给人决定）
- 有硬预算控制（默认 3 轮），不会无限循环；每次检索失败不终止循环，抗抖动
- ask_human 状态是持久化的，用户可以之后再决定——补资料、去掉那段、还是放弃，不是简单的报错

### Q4: 检索优化是怎么做的？效果提升了多少？

**回答思路（P14 已做完，按实测）：**
- 做了三层优化，都是可配置开关，默认关闭，不影响主流程
- 第一层是混合检索：BM25（2-gram 关键词）+ 向量语义匹配，用 RRF 算法融合，主要解决政策编号、日期这类专有名词"语义像但关键词不中"搜不准的问题
- 第二层是 Rerank 重排序：取前 20 个候选用 bge-reranker-v2-m3 交叉编码精排，提升排序精度
- 第三层是查询扩展：用 LLM 把 query 扩展成 3 种不同表述再检索合并，作为召回兜底（保留开关，更大语料下有用）
- 效果（自建 20 条评测集、easy/medium/hard 三级）：Recall@5 从 0.58 提到 0.89（+30pp），NDCG@5 从 0.57 提到 0.84；Rerank 单独把 MRR 从 0.66 提到 0.90。评测集可一键复跑（`go test -tags=integration ./agent/retrieve/eval/`），数字不是编的
- 加分细节：评测时发现"同池内 RRF 前移有限"这类问题，通过把 BM25 高分段集中在多个相关切片的事实来解释提升来源；查询扩展实测无增量后如实记录为"边际收益递减"，比硬凑数字更可信

### Q5: 这个项目你做了多久？最大的难点是什么？

**回答思路：**
- 前后做了大概 3 个月，从需求分析到架构设计到编码到测试，都是自己一个人完成
- 最大的难点是**证据溯源的端到端一致性**——从文档切片怎么切、检索粒度到哪一级、撰写时怎么建立绑定、修订时怎么维护绑定不错位，整个链路都要考虑到句子粒度
- 特别是 P08 那个稳定句身份的设计，一开始用下标定位句子，后来发现用户一旦删除中间一句，所有后面的句子下标都变了，证据就挂错了——后来改成了用稳定的 sentence_id 做身份锚，序列操作（增删改移）都基于身份而不是位置，这个问题才彻底解决
